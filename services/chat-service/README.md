# Chat Service

Внутренний HTTP-сервис чата Plotina на Go. WebSocket-соединениями с браузером
управляет API Gateway.

## Требования

- Go 1.27 или новее.
- Внешние зависимости для этого этапа не нужны.

## Запуск

В папке `chat-service` выполните:

```bash
go run ./cmd/chat
```

По умолчанию сервер слушает `:8080`. Адрес задаётся переменной окружения
`HTTP_ADDR`:

```bash
HTTP_ADDR=127.0.0.1:6767 go run ./cmd/chat
```

## Проверка

```bash
curl -i http://localhost:8080/health
```

Ожидаемый результат: `200 OK`, тело ответа — `i'm still standing`.
Этот маршрут проверяет только доступность HTTP-сервера.
Если сервер запущен на другом порту, замените `8080` в команде проверки.

## Ручная проверка сообщений

Из папки `chat-service` запустите отдельную консольную демонстрацию:

```bash
go run ./cmd/chat-demo
```

Введите текст и нажмите Enter. Программа вызовет ту же логику `SendMessage`,
что проверяют тесты, и покажет commandId, duplicate, messageId, roomId, userId,
text, messageSeq и sentAt. HTTP-сервер для этого запускать не нужно.

Пример ввода:

```text
Привет
Ещё сообщение
/retry
/as user-2
Сообщение другого участника
/as user-3
Сообщение другой комнаты
/quit
```

Номера сообщений будут `1, 2, 2, 3, 1`: повтор возвращает прежнее сообщение
с `duplicate: true`, участники room-1 используют общий счётчик, а room-2 — свой.
Доступны `/help` и `/quit`. После смены пользователя команда `/retry` сбрасывается,
пока выбранный пользователь не отправит новое сообщение.

Это только локальные команды демонстрации, не реализация будущих команд чата.
Демонстрация использует заглушку членства и отдельное хранилище в памяти:
данные не разделяются с другими запусками и теряются при выходе.

## Структура

```text
cmd/chat/main.go             — конфигурация адреса и запуск сервера
cmd/chat-demo/main.go        — интерактивная проверка сообщений в терминале
internal/httpapi/handler.go  — HTTP-маршруты и обработчик /health
internal/chat/              — модели, ошибки и обработка текстовых сообщений
internal/rooms/fake.go       — заглушка проверки участника по заданным токенам
internal/storage/memory.go  — временное хранилище сообщений и результатов команд
```

## Обработка сообщений: текущий этап

`chat.Service.SendMessage` проверяет обязательные поля, запрашивает подтверждение
членства и сверяет пользователя и комнату с результатом проверки. Затем передаёт
сообщение в хранилище. Текст пока сохраняется без изменений; сообщения, состоящие
только из пробельных символов, отклоняются.

Внутренние модели:

- `SendCommand` — комната, пользователь, токен сессии, commandId и текст.
- `Membership` — подтверждённые комната и пользователь.
- `Message` — messageId, комната, автор, текст, серверное время UTC и messageSeq.
- `SendResult` — commandId, признак duplicate и сохранённое сообщение.

Это модели Go, а не согласованный сетевой JSON-контракт. Новых HTTP-маршрутов
пока нет; сервер по-прежнему предоставляет только `/health`. Бизнес-логика
проверяется через тесты без Gateway и Room Service.

Хранилище назначает последовательные messageSeq отдельно для каждой комнаты.
Повтор `(roomId, userId, commandId)` с тем же текстом возвращает прежнее сообщение
с `duplicate = true`, не расходуя следующий номер. Другой текст с тем же ключом
вызывает ошибку. Проверка членства выполняется и при повторе команды.

Временное хранилище синхронизирует запись блокировкой в памяти одного экземпляра.
Данные теряются при его пересоздании или перезапуске программы, поэтому это ещё
не реализация транзакционных гарантий ТР. Токены в хранилище не передаются.
Заглушка проверки членства принимает только явно заданные токены; она не проверяет
реальное подключение участника или закрытие комнаты. В HTTP-сервер она не включена.

## Тесты

```bash
go test -race ./...
go vet ./...
```

Тесты проверяют отправку текста, отказы в доступе, обязательные поля, отдельные
счётчики комнат, повтор команды, конфликт текста, одновременные повторы и отмену
операции.
