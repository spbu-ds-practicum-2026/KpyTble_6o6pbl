# Chat Service

Внутренний HTTP-сервис чата Plotina на Go. WebSocket-соединениями с браузером
управляет API Gateway.

**Для совместной интеграции:** [порядок запуска и проверки](docs/INTEGRATION.md),
[OpenAPI для Gateway / Postman](docs/openapi.yaml),
[страница проверки WebSocket Gateway](docs/gateway-check.html).

**Графический чат без запуска backend:**

```bash
go run ./cmd/chat-web
```

Открыть `http://127.0.0.1:8099`. Компактный виджет с авторами сообщений, вводом,
автопрокруткой и кнопкой-заглушкой стикеров. По умолчанию работает локальный
деморежим; в настройках можно подключить WebSocket Gateway с токеном.
[Подробнее об интерфейсе и встраивании](web/README.md).

## Требования

- Go 1.27 или новее.
- Драйвер PostgreSQL — `github.com/jackc/pgx/v5`, Go скачивает зависимости автоматически.
- Для консольной демки на памяти сервер БД не нужен. HTTP-сервис использует
  PostgreSQL и Room Service; локальная конфигурация Docker Compose поднимает
  PostgreSQL 17 для чата. Профиль Compose `app` дополнительно собирает приложение
  и применяет миграции перед запуском.

## Запуск

Все команды выполняются из папки `services/chat-service` в Bash.
Поднимите PostgreSQL (Docker или собственная установка), задайте адреса
и примените миграции:

```bash
docker compose up -d --wait chat-db
export CHAT_DATABASE_URL='postgres://chat:chat-local@127.0.0.1:5433/chatdb?sslmode=disable'
export ROOM_SERVICE_URL='http://127.0.0.1:8000'
export HTTP_ADDR='127.0.0.1:6767'
go run ./cmd/chat-migrate
go run ./cmd/chat
```

Настройки:

| Переменная | Назначение |
| --- | --- |
| `CHAT_DATABASE_URL` | Обязательная строка подключения к собственной Chat DB |
| `ROOM_SERVICE_URL` | Обязательный базовый HTTP(S)-адрес Room Service |
| `HTTP_ADDR` | Адрес HTTP-сервера; по умолчанию `:8080`, в примере — `127.0.0.1:6767` |

Go-программа не загружает `.env` автоматически. Сервер проверяет подключение и
необходимые таблицы БД при запуске; недоступность БД, неприменённые миграции
или неверная конфигурация не дают ему запуститься.
Миграции применяются отдельно. Room Service вызывается при отправке сообщения
и чтении номера, а не при старте. Ctrl+C завершает сервер с ожиданием активных
запросов и закрытием подключения к PostgreSQL.

Альтернатива без локальной установки Go (Room Service запускается отдельно):

```bash
export ROOM_SERVICE_DOCKER_URL='http://host.docker.internal:8000'
docker compose --profile app up -d --build
```

Внутри контейнера `localhost` — сам контейнер, поэтому Room Service на хосте
доступен через host.docker.internal, а на другом компьютере — по его IP.
На Linux Room Service на хосте должен слушать интерфейс, доступный контейнеру.
Подробнее о сетях, портах, миграциях и остановке — в [инструкции интеграции](docs/INTEGRATION.md).

## Проверка

```bash
curl -i http://127.0.0.1:6767/health
curl -i http://127.0.0.1:6767/ready
```

Ожидаемый результат: `200 OK`, тело ответа — `i'm still standing`.
Этот маршрут проверяет только доступность HTTP-сервера.
Если сервер запущен на другом порту, замените `6767` в команде проверки.
`/health` не проверяет доступность зависимостей и не требует токена.
`/ready` возвращает JSON со статусом database и room_service: 200 при готовности
обоих, 503 при ошибке. Проверка Room Service использует его `/health`, а не
права конкретного участника. Оба диагностических маршрута доступны без токена.

Для автоматической проверки полной HTTP-цепочки:

```bash
python3 scripts/integration_smoke.py --create-room
```

Скрипт создаёт тестовые комнаты в работающем Room Service, записывает сообщения,
проверяет ответы и закрывает только созданные комнаты. Токены не печатает.
Режим с существующей сессией описан в инструкции интеграции.

## HTTP API чата

| Метод и путь | Назначение |
| --- | --- |
| `POST /rooms/{room_id}/messages` | Отправить текстовое сообщение |
| `GET /rooms/{room_id}/messages/seq` | Получить последний сохранённый messageSeq |

Оба маршрута требуют `Authorization: Bearer <token>` и проверки членства через
Room Service. В пустом чате GET возвращает `{"messageSeq":0}`; чтение не создаёт
строку счётчика и не расходует номера. POST принимает только command_id и text,
автор определяется по токену. Успешные ответы — HTTP 200 и JSON по контракту.

Для ручной проверки Room Service должен быть запущен с согласованным membership
endpoint. Возьмите настоящий room_id и token из ответа создания комнаты или
подключения в Room Service; значения `alice-token` из документа — лишь примеры.

```bash
export ROOM_ID='room-id-из-Room-Service'
read -r -s -p 'Токен участника: ' SESSION_TOKEN

curl -i "http://127.0.0.1:6767/rooms/$ROOM_ID/messages/seq" \
  -H "Authorization: Bearer $SESSION_TOKEN"

curl -i -X POST "http://127.0.0.1:6767/rooms/$ROOM_ID/messages" \
  -H "Authorization: Bearer $SESSION_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"command_id":"manual-1","text":"Привет!"}'
```

Повторите последний запрос без изменений — вернётся то же сообщение с
`duplicate:true`. С прежним command_id и другим текстом получится HTTP 409
`command_id_conflict`. Для следующего нового сообщения используйте новый ID,
например `manual-2`. GET после отправки покажет актуальный номер.

Все обработанные ошибки имеют вид:

```json
{"error":{"code":"unauthorized","message":"Токен отсутствует или недействителен"}}
```

| HTTP | code | Причина |
| --- | --- | --- |
| 401 | unauthorized | Нет Bearer-токена или сессия недействительна |
| 403 | wrong_room | Токен не подтверждает участие в этой комнате |
| 409 | room_closed | Room Service отклонил запрос из-за закрытой комнаты |
| 409 | command_id_conflict | Тот же ID использован с другим текстом |
| 422 | invalid_payload | Неверный JSON, лишние поля, пустые или неверные параметры |
| 413 | payload_too_large | Тело запроса больше 64 КиБ |
| 415 | unsupported_media_type | У POST нет Content-Type: application/json |
| 503 | room_service_unavailable | Room Service недоступен или вернул некорректный ответ |
| 503 | storage_unavailable | Ошибка обращения к Chat DB |
| 504 | room_service_timeout | Проверка участника заняла больше 3 секунд |
| 504 | request_timeout | Обработка команды превысила 5 секунд |
| 408 | request_cancelled | Запрос отменён |
| 404 / 405 | not_found / method_not_allowed | Неверный путь или метод |
| 500 | internal_error | Неожиданная внутренняя ошибка |

Лимит 64 КиБ относится ко всему JSON-телу, а не к частоте отправки. Это технический
предел текущей реализации. При таймауте или недоступности БД результат записи
может быть неизвестен: повтор отправляется с прежними command_id и текстом.
Внешний JSON не содержит внутренних ошибок БД, токенов и текстов ошибок сети.
В ответах есть X-Request-ID; в JSON-логах — этот ID, метод, шаблон маршрута,
статус и длительность. Тела сообщений, токены и query-параметры не логируются.
Текст с нулевым символом и некорректная UTF-8 строка отклоняются как invalid_payload
до обращения к хранилищу.
Эта часть API не держит WebSocket-соединения и не рассылает сообщения клиентам:
Gateway вызывает HTTP-маршруты и рассылает полученный результат.

## Ручная проверка сообщений

Из папки `chat-service` запустите отдельную консольную демонстрацию:

```bash
go run ./cmd/chat-demo
```

Введите текст и нажмите Enter. Программа вызовет ту же логику `SendMessage`,
что проверяют тесты, и покажет command_id, duplicate, message_id, room_id,
participant_id, text, messageSeq и created_at. HTTP-сервер для этого запускать
не нужно. Автор сообщения определяется по токену через заглушку Room Service,
а не передаётся в команде отправки.

При запуске существует и выбран только `user-1` (`participant-1`, роль `host`)
в `room-1`. Имена `user-n` используются только для управления демкой.
Других пользователей
нужно добавлять вручную. `/add n` добавляет нового пользователя в `room-n`, даже
если этот номер комнаты ещё не использовался. Настоящая комната в Room Service
при этом не создаётся. Для переключения на добавленного пользователя нужен `/as`.

Пример ввода:

```text
Привет
Ещё сообщение
/retry
/add 1
/as user-2
Сообщение другого участника
/add 2
/as user-3
Сообщение другой комнаты
/quit
```

В пустом хранилище номера сообщений будут `1, 2, 2, 3, 1`: повтор возвращает прежнее сообщение
с `duplicate: true`, участники room-1 используют общий счётчик, а room-2 — свой.

Команды демонстрации:

| Команда | Действие |
| --- | --- |
| Обычный текст + Enter | Отправить сообщение от выбранного пользователя |
| `/add n` | Добавить нового пользователя в `room-n`; `n` — положительное целое число |
| `/as user-n` | Переключиться на существующего пользователя |
| `/users` | Показать пользователей, их комнаты, participant_id, роли и демонстрационные токены |
| `/retry` | Повторить последнюю отправку с прежним commandId |
| `/help` | Показать подсказку |
| `/quit` | Завершить программу |

После успешного `/add` или `/as` последняя команда для `/retry` сбрасывается.
Для повтора сначала отправьте новое сообщение. Добавление и переключение
пользователей не удаляют сообщения и не сбрасывают счётчики комнат.

Это только локальные команды демонстрации, не реализация будущих команд чата.
Добавленные пользователи имеют роль `member`; демка не реализует назначение
ведущего новой комнаты или передачу роли. Строки, начинающиеся с `/`, пока
обрабатываются самой демкой и не передаются в `chat.Service`.
Демонстрация использует заглушку членства. Без `CHAT_DATABASE_URL` сообщения
хранятся в памяти: данные не разделяются с другими запусками и теряются при
выходе. Если переменная уже задана, удалить её для режима памяти можно командой
`unset CHAT_DATABASE_URL` в Bash.

## PostgreSQL: запуск и ручная проверка

Все команды ниже выполняются из `services/chat-service` в Bash.
Если Docker установлен, поднимите отдельную базу чата:

```bash
docker compose up -d --wait chat-db
```

Используется порт `127.0.0.1:5433`, чтобы не занимать стандартный `5432` базы
Room Service. Данные чата находятся в собственном volume `chat_pgdata`.
Chat Service не обращается к базе Room Service и не создаёт в ней таблицы.

Задайте строку подключения и примените миграции:

```bash
export CHAT_DATABASE_URL='postgres://chat:chat-local@127.0.0.1:5433/chatdb?sslmode=disable'
go run ./cmd/chat-migrate
```

При повторном запуске уже применённые миграции пропускаются. Миграции встроены
в программу; запуск не зависит от текущего пути к SQL-файлам. Их применение
выполняется отдельно, не при каждой отправке сообщения. `.env.example` содержит
пример настроек, но программа не загружает `.env` автоматически.

Запустите ту же демку с установленной переменной:

```bash
go run ./cmd/chat-demo
```

В начале появится `Хранилище: PostgreSQL`. Отправьте сообщение, повторите его
через `/retry`, выйдите через `/quit` и запустите демку снова. Следующее новое
сообщение в `room-1` получит следующий номер, а не `1`. Для нового действия
демка создаёт command_id с уникальным префиксом запуска, поэтому перезапуск
не конфликтует со старыми командами. `/retry` повторяет только последнюю команду
текущего запуска; после выхода ссылка на неё не сохраняется.

Пользователи, роли и комнаты демки по-прежнему условные и создаются заново
в памяти. При одинаковом номере комнаты разные запуски демки используют один
счётчик в Chat DB, но это не настоящая интеграция с Room Service.

Посмотреть сохранённые сообщения:

```bash
docker compose exec chat-db psql -U chat -d chatdb -P pager=off -c \
  'SELECT room_id, message_seq, participant_id, text, created_at FROM chat_messages ORDER BY room_id, message_seq;'
```

Остановить локальную базу с сохранением данных:

```bash
docker compose down
```

Docker необязателен: можно использовать уже установленную PostgreSQL и указать
собственный `CHAT_DATABASE_URL`. Миграциям нужны права на создание таблиц в
собственной базе чата. Пример пароля и `sslmode=disable` относятся только
к локальному запуску из этого раздела.

## Схема и транзакции

| Таблица | Назначение |
| --- | --- |
| `chat_room_counters` | Последний messageSeq для каждой комнаты |
| `chat_messages` | ID, комната, автор, порядковый номер, текст и время сообщения |
| `chat_commands` | Исходный текст и ссылка на сохранённое сообщение по `(room_id, participant_id, command_id)` |
| `chat_schema_migrations` | Список применённых миграций и контрольные суммы SQL |

ID комнат и участников хранятся как `TEXT`: это внешние идентификаторы, а не
копия таблиц Room Service. Межсервисных внешних ключей нет. Ограничения базы
запрещают дубли `(room_id, message_seq)` и повтор ключа команды. Внешний ключ
связывает результат команды с сообщением той же комнаты и участника.

`postgres.Repository.Append` выполняет действия одной транзакцией:

1. Создаёт счётчик комнаты, если он ещё отсутствует.
2. Блокирует строку счётчика через `SELECT ... FOR UPDATE`.
3. Проверяет результат команды: повтор возвращает прежнее сообщение, другой
   исходный текст с тем же ключом вызывает `ErrCommandIDConflict`.
4. Для новой команды увеличивает счётчик, записывает сообщение и результат.
5. Фиксирует транзакцию. При ошибке все её изменения откатываются.

Блокировка находится в PostgreSQL, поэтому работает между разными подключениями
и экземплярами хранилища. Разные комнаты используют разные строки счётчика.
Номера выдаются в порядке захвата блокировки, а не обязательно нажатий в браузере.
При ошибке фиксации клиент не может считать действие невыполненным: повтор должен
использовать прежние command_id и параметры.

Токен в базу не передаётся. Результат команды хранится как ссылка на неизменяемое
сообщение, поэтому повтор возвращает прежние ID, messageSeq, текст и время.
Автоматическое удаление данных завершённой комнаты пока не реализовано.

SQL находится в `migrations/001_init.up.sql`. Применённые файлы не редактируются:
для изменения схемы нужно добавить следующий `*.up.sql`. Команда миграций
проверяет контрольные суммы и отклоняет изменение уже применённого файла.
`001_init.down.sql` содержит обратный SQL; автоматической команды отката нет.

## Обработка сообщений: текущий этап

`chat.Service.SendMessage` проверяет обязательные поля и запрашивает подтверждение
членства по комнате и токену. Комната должна совпадать с ответом Room Service,
а participant_id — быть непустым. Автор сообщения берётся исключительно из
результата проверки. Затем сообщение передаётся в хранилище. Текст пока
сохраняется без изменений; сообщения, состоящие только из пробельных символов,
отклоняются. Стикеры и команды будут приходить в том же поле text, но их разбор,
исполнение и цензура пока не реализованы.

Внутренние модели:

- `SendCommand` — комната и токен из транспортного слоя, command_id и text из тела
  запроса. Полей user_id и participant_id во входящей команде нет.
- `Membership` — ответ Room Service: room_id, participant_id, display_name,
  role (`host` / `member`), connected.
- `Message` — message_id, participant_id, text, серверное время UTC created_at
  и messageSeq. RoomID хранится внутри сервиса, но не включается в JSON сообщения.
- `SendResult` — command_id, признак duplicate и сохранённое message.
- `Sequence` — текущий messageSeq для ответа GET.

Имена JSON-полей моделей приведены к согласованному контракту. Пример тела
запроса отправки:

```json
{"command_id":"cmd-7","text":"Привет!"}
```

Пример результата обработки:

```json
{
  "command_id": "cmd-7",
  "duplicate": false,
  "message": {
    "message_id": "message-1",
    "messageSeq": 43,
    "participant_id": "participant-1",
    "text": "Привет!",
    "created_at": "2026-11-19T12:00:00Z"
  }
}
```

RoomID и SessionToken не кодируются в JSON тела команды: HTTP-обработчик
получает их из URL и заголовка `Authorization: Bearer <token>`. При запуске
`cmd/chat` обработчики используют настоящий HTTP-клиент Room Service и
PostgreSQL-хранилище. Заглушка используется только в консольной демке и тестах.

Хранилище назначает последовательные messageSeq отдельно для каждой комнаты.
Повтор `(room_id, participant_id, command_id)` с тем же текстом возвращает прежнее сообщение
с `duplicate = true`, не расходуя следующий номер. Другой текст с тем же ключом
вызывает ошибку. Проверка членства выполняется и при повторе команды.

Временное хранилище синхронизирует запись блокировкой в памяти одного экземпляра.
Данные теряются при его пересоздании или перезапуске программы. PostgreSQL-хранилище
реализует транзакционную запись и постоянную дедупликацию, как описано выше.
Токены в хранилища не передаются.
Заглушка проверки членства принимает только явно заданные токены и возвращает
настроенные данные участника; она не отслеживает реальное подключение или закрытие
комнаты. Поле connected сохраняется в Membership, но отдельная политика для
connected=false ещё не определена и сейчас сервис его не использует. Заглушка
в HTTP-сервер не включена.

## HTTP-клиент Room Service

`rooms.NewHTTPClient(baseURL, timeout)` создаёт проверку членства через настоящий
HTTP-запрос. Например, при адресе `http://localhost:8000` клиент выполняет:

```text
GET /internal/rooms/{room_id}/membership
Authorization: Bearer <token>
```

Из успешного JSON-ответа извлекаются room_id, participant_id, display_name,
role и connected. Проверяются совпадение комнаты, непустой participant_id,
роль host/member и наличие логического connected. Значение connected=false
само по себе не является отказом: соответствующая политика пока не согласована.

Клиент реализует тот же `MembershipChecker`, что и заглушка. Его можно передать
в `chat.NewService` без изменения логики отправки сообщений. Адрес и положительный
таймаут задаются при создании; таймаут охватывает запрос и чтение тела ответа.
Автоматических повторов и переходов по перенаправлениям нет. Токен передаётся
только в заголовке, а произвольный текст ответа Room Service не включается
в возвращаемые ошибки.

| Ответ Room Service | Ошибка внутри Chat Service |
| --- | --- |
| 401 unauthorized | ErrUnauthorized |
| 403 wrong_room | ErrForbidden |
| 409 room_closed | ErrRoomClosed |
| Истёк таймаут | ErrRoomServiceTimeout |
| Ошибка соединения, неожиданный HTTP-статус или некорректный ответ | ErrRoomServiceUnavailable |

Ошибки HTTP распознаются по согласованному телу
`{"error":{"code":"...","message":"..."}}`. Неизвестный код или несовпадение
кода со статусом считается ошибкой интеграции. Отмена через context передаётся
вызывающему коду как context.Canceled.

В `cmd/chat` HTTP-клиент подключён к `chat.Service` вместе с PostgreSQL.
Консольная демка по-прежнему использует локальную заглушку.

## Тесты

```bash
go test -race ./...
go vet ./...
```

Тесты проверяют отправку текста, отказы в доступе, обязательные поля, отдельные
счётчики комнат, повтор команды, конфликт текста, одновременные повторы и отмену
операции. Также проверяются определение автора по токену, JSON-форматы запроса,
результата и membership и отсутствие токена и комнаты в JSON тела команды.
Тесты `internal/httpapi` проверяют отправку и повторы через HTTP, получение номера,
проверку токена на обоих маршрутах, неверные тела, подмену автора и формат ошибок.

Тесты HTTP-клиента запускают локальный тестовый HTTP-сервер через httptest;
настоящий Room Service для них не нужен:

```bash
go test -race -count=1 -v ./internal/rooms
```

Проверяются путь и Bearer-заголовок, успешный ответ, ошибки доступа и закрытой
комнаты, таймаут чтения тела, неверные ответы, отмена, недоступность сервера
и запрет перенаправлений. Отдельный сценарий связывает HTTP-клиент с chat.Service
и хранилищем в памяти: отказ не создаёт сообщение, автор берётся из ответа
Room Service, а при повторе команды доступ проверяется заново. Реальная
интеграция с работающим Room Service этими тестами не подтверждается.

Интеграционные тесты PostgreSQL запускаются только при заданной
`CHAT_TEST_DATABASE_URL`; иначе явно пропускаются. Для локальной базы из Compose:

```bash
CHAT_TEST_DATABASE_URL="$CHAT_DATABASE_URL" go test -race -count=1 -v ./internal/storage/postgres
```

Тесты создают отдельную случайную схему на каждый сценарий и удаляют её после
завершения, не используя рабочие таблицы приложения. Тестовой роли нужны права
на создание схем. Проверяются миграции и их повторное применение, сохранность
после открытия нового подключения, конфликт command_id, откат транзакции,
счётчики разных комнат, отмена операции и конкурентные записи через два пула.
Сценарий `TestPostgresHTTPFlow` связывает HTTP-обработчики, HTTP-клиент Room Service
и настоящую Chat DB: проверяет отправку, повтор после пересоздания компонентов,
чтение счётчика и ошибки зависимостей. Сам Room Service в тесте заменён локальным
HTTP-сервером, поэтому совместимость с его реальным запуском проверяется отдельно.
