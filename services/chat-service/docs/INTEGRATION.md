# Подготовка и проверка интеграции

Рабочая папка: `services/chat-service`. Код других сервисов не изменяется.
Все команды терминала ниже — Bash. Python-скрипт работает на Python 3.9+ без
сторонних пакетов. Настоящие пароли и токены не коммитим.

Для обычного интерфейса чата можно запустить `go run ./cmd/chat-web` и открыть
http://127.0.0.1:8099. Он поддерживает деморежим и подключение к Gateway через
настройки. Ниже описана дополнительная страница с сырым журналом протокола;
её сервер используйте на другом порту, если графический чат уже запущен.

## 1. Что передать разработчику Gateway

- Базовый адрес Chat Service: `http://<адрес>:6767`.
- OpenAPI: [`openapi.yaml`](openapi.yaml) — можно импортировать в Postman.
- `POST /rooms/{room_id}/messages`, Bearer-токен участника, тело
  `{"command_id":"cmd-7","text":"Привет!"}`.
- Ответ HTTP 200:

```json
{
  "command_id": "cmd-7",
  "duplicate": false,
  "message": {
    "message_id": "...",
    "messageSeq": 1,
    "participant_id": "...",
    "text": "Привет!",
    "created_at": "2026-11-25T12:00:00Z"
  }
}
```

- Автор не передаётся клиентом. Chat Service проверяет токен через Room Service.
- `GET /rooms/{room_id}/messages/seq` с тем же Bearer-токеном возвращает
  `{"messageSeq":1}`; для пустого чата — 0. command_id не нужен.
- У `messageSeq` намеренно camelCase; остальные поля ответа — snake_case.
- Gateway возвращает автору `commandConfirm` с commandId/duplicate/message,
  участникам — `sendMessage` с message. Ни token, ни command_id в рассылку
  участникам не добавляются. Автор тоже получает сообщение в общей рассылке.
- При повторе сохраняются исходные command_id и text. Возвращённое сообщение
  имеет прежние message_id/messageSeq/created_at. Дедупликация — по комнате,
  участнику и command_id. Другой текст с тем же ключом — HTTP 409.
- При сетевом сбое/503/504 нельзя считать действие невыполненным. Повторять
  нужно тот же ID, а не создавать новый. Автоповторы — с паузой и ограничением,
  без бесконечного цикла.
- HTTP-ошибки — `{"error":{"code":"...","message":"..."}}`. Gateway
  переносит error в соответствующий commandConfirm.
- Необязательный `X-Request-ID` (до 64 букв/цифр, `-`, `_`) возвращается в
  ответе и записывается в лог. Это диагностика, не новый ID команды.

Коды основных ошибок: 401 unauthorized, 403 wrong_room, 409 room_closed,
409 command_id_conflict, 422 invalid_payload, 503 room_service_unavailable,
503 storage_unavailable, 504 room_service_timeout/request_timeout.
POST требует application/json; полный JSON — до 64 КиБ. Дополнительные поля
запрещены. Частотных ограничений отправки сейчас нет.

## 2. Что должно быть у Room Service

```text
GET /health -> 200 {"status":"ok"}

GET /internal/rooms/{room_id}/membership
Authorization: Bearer <token>
```

Успешный membership:

```json
{
  "room_id": "...",
  "participant_id": "...",
  "display_name": "Alice",
  "role": "host",
  "connected": true
}
```

Проверить совпадение фактической реализации с этим JSON, особенно participant_id,
role и connected. Ошибки должны иметь согласованную оболочку error:
401 unauthorized, 403 wrong_room, 409 room_closed. Другой код/формат считается
ошибкой интеграции и превращается в 503 room_service_unavailable.

Для connected=false пока нет отдельного решения: Chat Service возвращает данные
участника без дополнительного запрета. Членство вышедшего участника и закрытая
комната должны отклоняться Room Service. Между проверкой членства и записью в
Chat DB общей транзакции нет: одновременный выход может пересечься с уже
проверенной отправкой. Это ограничение текущего прототипа.

## 3. Запуск без контейнера приложения

Нужны Go 1.27+, работающий Room Service и PostgreSQL (можно из Docker).

```bash
docker compose up -d --wait chat-db
export CHAT_DATABASE_URL='postgres://chat:chat-local@127.0.0.1:5433/chatdb?sslmode=disable'
export ROOM_SERVICE_URL='http://127.0.0.1:8000'
export HTTP_ADDR='127.0.0.1:6767'
go run ./cmd/chat-migrate
go run ./cmd/chat
```

Если Go-сервис нужен на других компьютерах в общей локальной сети, задайте
`HTTP_ADDR=0.0.0.0:6767`. Коллеги используют IP вашего компьютера, а не localhost.
Проверьте разрешение порта в сетевом экране. Не публикуйте этот учебный сервис
в интернет: сервисная аутентификация и TLS на входе сейчас не настроены.

При старте проверяется схема Chat DB. Если миграции не применены, запуск
останавливается с подсказкой. Room Service может ещё не работать: процесс
запустится, но /ready и команды будут сообщать о недоступности.

## 4. Запуск приложения и БД через Docker Compose

Room Service сначала запускается отдельно. Если он работает на хосте Linux,
он должен слушать доступный контейнеру интерфейс (обычно `0.0.0.0:8000`,
а не только `127.0.0.1`).

```bash
export ROOM_SERVICE_DOCKER_URL='http://host.docker.internal:8000'
docker compose --profile app up -d --build
docker compose --profile app ps -a
docker compose --profile app logs -f chat chat-migrate
```

Compose поднимает Chat DB, выполняет одноразовый chat-migrate и только после
успешной миграции запускает chat. У chat-migrate статус Exited (0) — нормально.
Дождитесь статуса healthy у chat: он основан на /ready. Если Room Service ещё
недоступен, контейнер продолжит работать, но будет unhealthy до восстановления.

Адрес приложения с хоста — `http://127.0.0.1:6767`. Внутри контейнера Chat DB
имеет адрес `chat-db:5432`. `localhost` внутри контейнера обозначает сам
контейнер: для Room Service на хосте используется host.docker.internal;
для другого компьютера — его IP; в общей Docker-сети — DNS-имя Room Service.
Gateway из другого Compose-проекта не увидит имя chat автоматически: нужна
общая сеть либо доступный опубликованный адрес.

Для доступа коллег по локальной сети перед запуском задайте `CHAT_BIND_IP=0.0.0.0`.
Если 6767 занят, задайте CHAT_PORT и сообщите новый порт Gateway. Настройка
ROOM_SERVICE_DOCKER_URL относится только к Compose; ROOM_SERVICE_URL — к
локальному запуску Go и Python-скрипту. Room DB не подключается к Chat Service.

Остановка без удаления данных:

```bash
docker compose --profile app down
```

Не используйте `down -v`, если нужно сохранить данные проверки. После изменения
Go-кода/миграций пересоберите `docker compose --profile app up -d --build`.
Compose читает .env для подстановок, Go и Python сами этот файл не загружают.

## 5. Диагностика до проверки сообщений

```bash
curl -i http://127.0.0.1:6767/health
curl -i http://127.0.0.1:6767/ready
```

- /health — прежний текст, 200, процесс жив. БД и Room Service не проверяются.
- /ready — 200, если схема БД доступна и Room Service отвечает на /health;
  иначе 503. Например:

```json
{"status":"not_ready","checks":{"database":"ok","room_service":"unavailable"}}
```

Ready не подтверждает правильность membership и права конкретного участника.
Он не заменяет сквозную проверку ниже. Диагностика не требует токена и не
показывает адреса/пароли/тексты внутренних ошибок.

Логи HTTP — JSON: request_id, method, шаблон route, status, duration_ms.
Токены, URL с query-параметрами и тексты сообщений не логируются. По X-Request-ID
можно сопоставить запрос Gateway с ответом Chat. Успешный /health после остановки
зависимости ожидаем: недоступность покажут /ready и прикладные запросы.

## 6. Сквозная HTTP-проверка

Самый полный сценарий создаёт две временные комнаты в Room Service, подключает
участника, проверяет отправку/повтор/конфликт/общий счётчик/ошибочные токены/
чужую комнату/закрытие. Он пишет тестовые сообщения в Chat DB и закрывает только
созданные им комнаты (данные сообщений автоматически не удаляются):

```bash
python3 scripts/integration_smoke.py --create-room
```

Адреса по умолчанию — Chat 127.0.0.1:6767 и Room 127.0.0.1:8000.
Их можно изменить:

```bash
python3 scripts/integration_smoke.py --create-room \
  --chat-url http://127.0.0.1:6767 --room-url http://127.0.0.1:8000
```

Без создания и закрытия комнат используйте уже существующую сессию:

```bash
export CHAT_SMOKE_ROOM_ID='настоящий-room-id'
read -r -s -p 'Токен участника: ' CHAT_SMOKE_TOKEN
export CHAT_SMOKE_TOKEN
python3 scripts/integration_smoke.py
unset CHAT_SMOKE_TOKEN
```

Этот режим всё равно сохраняет одно тестовое сообщение, но не закрывает
комнату. В общей комнате допускает сообщения других участников между шагами.
Токен в отчёт не выводится. Успех — PASS по шагам и код завершения 0;
при проблеме — FAIL и ненулевой код. Скрипт использует настоящий Room Service
по указанному адресу, не подменяет его.

## 7. Проверка с Gateway и двумя вкладками

После подключения HTTP-клиента Chat Backend на стороне Gateway:

1. Создать комнату и подключить второго участника, получить два разных токена.
2. Запустить локальную страницу диагностики:

```bash
python3 -m http.server 8100 --bind 127.0.0.1 --directory docs
```

3. Открыть `http://127.0.0.1:8100/gateway-check.html` в двух вкладках. Если Gateway
   ограничивает Origin, согласовать разрешение http://127.0.0.1:8100. Страница
   не обходит проверку Origin и не изменяет конфигурацию Gateway.
4. Указать WebSocket Gateway, вставить свой токен в каждую вкладку, подключиться.
   Страница отправит getState с token; команды авторизации старого каркаса
   session.authenticate здесь не используются.
5. Отправить сообщение из первой вкладки, дождаться подтверждения и рассылки.
   Обе вкладки должны получить одинаковые message_id/messageSeq.
6. Нажать повтор: автор получает duplicate=true, номер не меняется; повторная
   рассылка может прийти, но полноценный frontend должен удалить дубли.
7. Нажать конфликт: commandConfirm.error.code=command_id_conflict, новой
   рассылки нет. getChatSeq возвращает последний номер без commandId.
8. Переподключить вкладку: initialMessageSeq должен соответствовать новому
   начальному номеру. Во время отключения история не загружается.

Страница показывает сырой обмен, не реализует финальный UI, клиентский буфер
или автопрокрутку. Повторные события в журнале допустимы. Heartbeat pig/pong
обрабатывается автоматически в точности по предоставленному контракту.

## 8. Минимум отказов, которые проверить вместе

- Перезапустить только Chat Service: GET seq прежний, повтор с прежним ID
  возвращает то же сообщение. Для проверки сохраните исходные ID и text.
- Остановить Room Service: Chat отвечает 503/504, видео зависит от своей цепочки;
  после восстановления повторить ту же команду.
- Остановить chat-db: Chat отвечает 503/504; управление видео через Gateway
  не должно блокироваться. Запустить БД снова и проверить прежнюю команду.
- Параллельная отправка от двух участников: разные messageSeq, общий порядок.
- Закрыть тестовую комнату: новые сообщения и чтение seq отклоняются по результату
  проверки Room Service. Повтор отправки также заново проверяет членство.

## 9. Что сейчас не выдавать за готовое

- Восстановление пропусков: есть чтение номера, но нет согласованного endpoint
  выдачи диапазона сообщений. Нужен контракт с Gateway; не добавляем его молча.
- Буферизация на подключении и initialMessageSeq — ответственность Gateway.
- Стикеры, выполнение команд и цензура пока не реализованы; text хранится как
  текст, включая строки с /. Служебные команды консоли — другая функциональность.
- Политика connected=false, закрытие/очистка данных Chat DB и доставка
  асинхронных событий требуют отдельного решения команды.
- Контейнеры не делают систему отказоустойчивой автоматически; общий Gateway
  и Room Service остаются зависимостями. /ready проверяет доступность, а не всю
  корректность интеграции.
